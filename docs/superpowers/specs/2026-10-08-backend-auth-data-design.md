# Pulse Backend, Auth & Data Migration

**Date:** 2026-10-08
**Status:** Draft
**Scope:** Sub-project 1 of 2. This spec covers the backend, authentication, database schema, and data migration from localStorage. Sub-project 2 (push notifications) will be specced separately once this is complete.

---

## Goal

Replace localStorage as the source of truth for all user data with a Supabase Postgres backend. Add user authentication so the app supports multiple users. Preserve the existing UX — the app should feel identical, just persistent and account-bound.

## Success Criteria

1. Users can sign up / sign in with Google OAuth or email/password.
2. All data (habits, completions, tasks, calendar events, profile) is stored per-user in Supabase.
3. Existing localStorage data is migrated to the user's account on first login.
4. After migration, the app reads/writes exclusively from Supabase.
5. Unauthenticated users see a sign-in screen — no anonymous usage.
6. Row-Level Security ensures users can only access their own data.
7. The existing Ultrahuman API proxy continues working unchanged.

## Authentication

### Providers

1. **Google OAuth** (primary) — users already encounter Google in the Google Calendar integration, so this is the natural default.
2. **Email/password** (fallback) — for users who don't want to use Google.

### Flow

1. App boots, checks `supabase.auth.getSession()`.
2. If no session, render a sign-in screen (replaces the main app content).
3. On successful auth, the app renders normally.
4. Session tokens are stored by the Supabase SDK in localStorage automatically and refreshed transparently.

### Auth Context

A new `AuthContext` provider wraps the app (outside `HabitsProvider`). It exposes:
- `user: User | null`
- `loading: boolean`
- `signInWithGoogle(): Promise<void>`
- `signInWithEmail(email, password): Promise<void>`
- `signUp(email, password): Promise<void>`
- `signOut(): Promise<void>`

### Sign-In Screen

Minimal dark-themed screen matching the app's glass aesthetic:
- App logo / "Pulse" title
- "Continue with Google" button
- Divider ("or")
- Email + password fields with sign-in / sign-up toggle
- No other navigation until authenticated

## Database Schema

All tables use `uuid` primary keys (generated by Supabase default `gen_random_uuid()`). All tables have a `user_id uuid references auth.users(id) on delete cascade` column. All tables have RLS enabled with a policy: `using (auth.uid() = user_id)`.

### `profiles`

| Column | Type | Notes |
|--------|------|-------|
| id | uuid | PK, default `gen_random_uuid()` |
| user_id | uuid | FK to auth.users, unique |
| name | text | Display name |
| avatar_url | text | Nullable, from OAuth provider or uploaded |
| created_at | timestamptz | default `now()` |

**RLS policies:**
- SELECT: `auth.uid() = user_id`
- INSERT: `auth.uid() = user_id`
- UPDATE: `auth.uid() = user_id`

**Trigger:** On new user signup, auto-create a profile row via a Supabase database trigger (`handle_new_user` function) that copies `raw_user_meta_data->>'full_name'` and `raw_user_meta_data->>'avatar_url'` from the auth.users row.

### `habits`

| Column | Type | Notes |
|--------|------|-------|
| id | uuid | PK |
| user_id | uuid | FK |
| name | text | not null |
| icon | text | not null, Phosphor icon name |
| color | text | not null, one of: red, blue, green, yellow, purple, orange |
| frequency | text | not null, 'daily' or 'weekly' |
| created_at | timestamptz | default `now()` |

### `completions`

| Column | Type | Notes |
|--------|------|-------|
| id | uuid | PK |
| user_id | uuid | FK |
| habit_id | uuid | FK to habits(id) on delete cascade |
| date | date | not null |

**Unique constraint:** `(user_id, habit_id, date)` — prevents double-completion.

### `tasks`

| Column | Type | Notes |
|--------|------|-------|
| id | uuid | PK |
| user_id | uuid | FK |
| label | text | not null |
| done | boolean | default false |
| created_at | timestamptz | default `now()` |

### `calendar_events`

| Column | Type | Notes |
|--------|------|-------|
| id | uuid | PK |
| user_id | uuid | FK |
| title | text | not null |
| date | date | not null |
| time | time | nullable |
| location | text | nullable |
| created_at | timestamptz | default `now()` |

## Client Data Layer

### Supabase Client

A single shared Supabase client instance, created in `src/lib/supabase.ts`:

```ts
import { createClient } from '@supabase/supabase-js';

export const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
);
```

Environment variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are set in `.env` (local) and Vercel environment settings (production).

### Hook Refactoring

Each existing hook/context that currently reads/writes localStorage will be refactored to use Supabase:

| Current | Refactored approach |
|---------|-------------------|
| `useHabits` (localStorage `pulse-habits`, `pulse-completions`) | Fetch from `habits` and `completions` tables. Mutations via `supabase.from('habits').insert/update/delete`. |
| `tasks` state in Home.tsx (localStorage `pulse-tasks`) | Extract to `useTasks` hook. Fetch from `tasks` table. |
| `localEvents` in Calendar.tsx (localStorage `pulse-calendar-events`) | Extract to `useCalendarEvents` hook. Fetch from `calendar_events` table. |
| `pulse-profile-name` in Settings.tsx | Read/write from `profiles` table. |

Each hook will:
1. Fetch data on mount with a Supabase query.
2. Expose mutation functions that write to Supabase and update local state optimistically.
3. Return a `loading` boolean for initial fetch.

### Shared Pattern

```ts
// Pseudocode for the pattern each hook follows
function useSupabaseTable<T>(table: string) {
  const [data, setData] = useState<T[]>([]);
  const [loading, setLoading] = useState(true);
  const { user } = useAuth();

  useEffect(() => {
    if (!user) return;
    supabase.from(table).select('*').eq('user_id', user.id)
      .then(({ data }) => { setData(data ?? []); setLoading(false); });
  }, [user]);

  // insert, update, delete functions that call supabase and setData optimistically
  return { data, loading, insert, update, remove };
}
```

This is illustrative — each hook will have its own shape, but the fetch-on-mount + optimistic-mutation pattern is consistent.

## Data Migration (localStorage to Supabase)

### When

On first successful login, before the app renders data. Runs once per user.

### How

1. Check if the user has any habits in Supabase (`select count(*) from habits where user_id = ?`).
2. If count is 0 and localStorage has `pulse-habits`, run the migration.
3. Migration reads all localStorage keys (`pulse-habits`, `pulse-completions`, `pulse-tasks`, `pulse-calendar-events`, `pulse-profile-name`) and batch-inserts into the corresponding tables.
4. ID mapping: localStorage habits have client-generated IDs. The migration generates new UUIDs for the Supabase rows but must map old habit IDs to new ones when inserting completions (which reference `habit_id`).
5. On success, clear the localStorage keys (or mark them as migrated with a `pulse-migrated` flag).
6. On failure, leave localStorage intact and show a toast. Set a `pulse-migration-pending` flag in localStorage. On next app load (while authenticated), if the flag is present, retry the migration automatically.

### Migration function

Lives in `src/lib/migrate.ts`. Called from `AuthContext` after session is established and before data hooks mount. Returns a promise that resolves when done.

## Error Handling

- **Network failures:** Supabase SDK returns errors on failed queries. Each hook surfaces errors via a returned `error` state. The UI shows a subtle toast or inline error — not a blocking modal.
- **Auth token expiry:** Supabase SDK handles refresh automatically. If refresh fails, the user is redirected to sign-in.
- **Migration failures:** Non-blocking. localStorage data is preserved. User can continue (data will be re-read from localStorage as fallback until migration succeeds).

## What This Spec Does NOT Cover

- **Push notifications** — sub-project 2, separate spec.
- **Google Calendar token storage in Supabase** — the current Google Calendar integration uses a client-side OAuth flow with tokens in localStorage. Moving that to Supabase is a future enhancement.
- **Real-time subscriptions** — not needed for a personal tracker. Standard fetch-on-mount is sufficient.
- **Offline support / sync** — the PWA service worker caches the app shell. Data requires connectivity. Offline writes are out of scope.
- **Admin panel** — single-product, no admin needs.
